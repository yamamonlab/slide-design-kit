# 運用の決まり

デザインシステムを増やしすぎず、それぞれの強みを薄めないための決まり。何を共通にし、何を持ち主に残し、どう増やし、どう見直すか。

## 2つの層

| 層 | 中身 | このキットのシステム |
|---|---|---|
| **基盤** | 変えない決まり、型、パターンの名前、図の幾何、選び方、運用 | Kiban |
| **個別のシステム** | 主役と題材で選ばれる見た目と得意技 | Kozu、余白、密図、標識、和色 |

## 何を共通にするか

| 区分 | 中身 | 置き場 |
|---|---|---|
| **共通（全システムが従う）** | 読みやすさの下限（4.5:1・3:1・24px）、文章の作法、1枚1メッセージ、型の構成と主役、パターンの名前と「何を見せるか」、図の量の上限と幾何、ノードの意味、デッキのチェックリスト、トークンの枠の名前、システムの選び方 | Kiban |
| **持ち主のもの（写さない）** | 色・書体・角・線・影、部品の実装、得意技（`routing.md` の表） | 各システム |
| **貸し借り（素材）** | 章扉の線画（Kozu）、記号のセット（標識） | 元のシステムに置いたまま、デッキにコピーして使う。出所は元に従う |

- **パターンは名前だけ共通。** Kiban の `patterns.md` には「何を見せるか」と見本のリンクだけを書く。実装（HTML・部品）は、そのパターンを実際に使ったシステムだけが持つ。
- **先回りして移植しない。** あるシステムのパターンが別のシステムのデッキで必要になったら、その時に、そのシステムの見た目で組み、`patterns.md` の見本欄に足す。使う予定のないシステムに見本を足さない。
- **得意技を借りたくなったら、システムを替える。** Kozu のデッキでグラフが主役のスライドが続くなら、Kozu にグラフ部品を足すのではなく、問い2に戻って密図を選び直す。1〜2枚だけなら Kiban `charts.md` の見本をそのシステムの色で使う。

## 増やし方

1. **まず既存の改定で足りるか。** ブランド・主催・イベントが違うだけなら、新しいシステムを作らず、近いシステムの色・ロゴ・名前だけを差し替えた「変種」にする。変種は「土台：〇〇」と書き、差分だけを持つ。
2. **新しいシステムは、新しい主役か場面があるときだけ。** `routing.md` の問い2でどれにも決まらない主役や場面が、別々のデッキで2回出たら作る（例：コードが主役の技術講義）。増えすぎたら、休止できるものを先に探す。
3. **作り方は `new-system.md`。** 作ったら `routing.md` の表と `library.md` に1行ずつ足す。

## 改定の流れ

- **Kiban を変えるとき：** 版を上げ（v1 → v1.1）、`library.md` の各システムの「追随」の欄に「要」「不要」を書く。決まりそのものを変えたら「要」、章や表を足しただけなら「不要」。
- **個別のシステムを変えるとき：** その README の「基盤との違い」を更新する。変種に効く変更（色・書体）は、変種の README の「土台との違い」を確かめる。
- **変種を変えるとき：** 土台を変えない。土台に足すべきだと思ったら、土台の改定として提案する。
- **どの変更も** 各システムの `design-system.json` の `lastChange` を更新する。

## 見直し

- **四半期ごと：** 各システムを最後に使ったデッキを見て、`library.md` の状態を更新する。
- **休止：** 半年どのデッキにも使われなかったシステムは「休止」にする。消さない。
- **アーカイブ：** 参考のためだけに残すもの。選び方の問い0（名指し）以外では使わない。
- **空のシステム：** 中身のないデザインシステムは目録に載せず、持ち主が削除する。
